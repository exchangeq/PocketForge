# quality-output.md · 高质量输出规范

> 适用于所有类型：游戏代码、系统代码、小说、教案、报告、脚本、文档。
> 判定标准只有一条：**用户拿到就能用，不用再返工**。

## 1. 交付前自检（逐条打勾）

1. **完整性**：没有 `TODO`、`待补`、`...此处省略`、空函数体、只剩注释的类。
2. **可运行 / 可读通**：代码能编译或至少能跑起来；文稿从第一句到最后一句逻辑闭合。
3. **一致性**：命名、术语、单位、时间线、人称、数值口径前后不打架。
4. **密度**：每段都有信息量；删掉任何一段，读者会缺东西。不写"综上所述""随着时代发展"这类填充句。
5. **具体**：给参数、给示例、给边界条件，不写"适当调整""根据需要优化"。
6. **格式**：Markdown 标题层级正确、表格对齐、代码块标注语言；文稿分章分节，不出现裸露的 `**`。

## 2. 反 AI 味清单（写作类）

- 禁用：赋能、闭环、抓手、维度升级、深度赋能、值得深思、不难发现。
- 少用：综上所述、总而言之、首先/其次/最后三件套。
- 句长交替：长句之后必须跟短句；不要连续三段同结构。
- 每 800 字至少一个具体细节（数字、地名、动作、对话、器物）。
- 对话要有人物自己的说话习惯，不要所有角色一个腔调。

## 3. 代码类硬要求

- 单文件职责单一，超过 400 行就拆。
- 所有 public 函数写清楚入参边界与失败返回，不吞异常。
- 涉及文件写入必须先建父目录；涉及外部命令必须给超时与失败提示。
- 给出运行/构建命令，并标注依赖版本；不写"自行安装依赖"。
- 引擎/系统层代码必须包含：主循环、时间步长、状态保存与恢复三件套。

## 4. 交付物结构

```
<项目>/
  README.md      # 是什么、怎么跑、目录说明
  PROJECT.md     # 交付定义与验收标准
  AGENTS.md      # 给下一个 AI 的接手说明
  plan.md        # 当前进度与下一步
```

正文交付时先给结论，再给依据，最后给下一步可执行动作；不要用"可能/也许"糊住不确定的地方，不确定就写"未验证"。

## 5. 禁止

- 禁止把用户没要求的功能塞进交付物（越界）。
- 禁止伪造测试结果、伪造运行截图、伪造数据来源。
- 禁止用省略号代替正文，禁止"同上""略"。
