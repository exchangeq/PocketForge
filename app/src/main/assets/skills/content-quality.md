# content-quality.md · 生成内容质量线

> 用户要的不是"看起来像"，是"能直接用"。任何写作、文档、代码、设计说明都按这份标准自检。

## 1. 四条硬线

1. **完整**：不许"以下是示例，你可以自行补充"。开头、主体、结尾都要落地；代码要能跑，文档要能读，方案要能执行。
2. **具体**：名词要具体（文件名、函数名、参数、页码、章节），数字要给出（尺寸、时长、字数、数值区间）。禁止"适当调整""根据实际情况"这类空话。
3. **有据**：引用用户提供的文档/数据要标出处（`docs/inbox/xxx.md` 第几节）；没有依据的判断要写明"推测"，不许编造 API、命令、引文、数据。
4. **去 AI 味**：不堆"首先/其次/总之"，不写"在当今时代"这类空转；句子长短交错，允许具体细节与个人化表达；不重复标题同义句。

## 2. 分体裁基线

| 体裁 | 最低要求 |
| --- | --- |
| 书稿/章节 | 单章 ≥3000 字，有场景、有冲突、有细节；人物说话符合各自口吻 |
| 技术文档 | 每节含目的、步骤、示例、常见错误；命令可直接复制 |
| 代码 | 有错误处理、有边界判断；不留 `// TODO` 除非用户要求占位 |
| 方案/策划 | 目标、路径、资源、风险、验收标准五项齐全 |
| 文案 | 一句主张 + 三条支撑；不喊口号，给具体利益点 |

## 3. 自检五问（交付前逐条过）

- 删掉标题，读者还能看懂主体吗？
- 有没有三处以上能让用户直接执行的细节？
- 有没有一句是可以套在任何一个项目上的废话？删掉。
- 引用的文件、数据、接口是否真实存在（在工作区或用户文档里能查到）？
- 用户拿到这份东西，下一步知道做什么吗？

## 4. 禁止

- 不写"由于篇幅限制"来截断。
- 不用占位符冒充成品（`xxx`、`待补充`、`示例1`）。
- 不把用户原话改写成空泛总结后当交付。
